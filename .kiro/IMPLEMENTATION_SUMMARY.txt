CRITICAL INVARIANTS ENFORCED
═══════════════════════════════════════════════════════════════════════════════

1. TOTAL ORDERING
   - lastSequence strictly increases
   - Rejects any seq ≤ lastSequence (3 places: store, type, contract)
   - Enforced by: vector clock + database UNIQUE constraint

2. BALANCE CONSERVATION  
   - party_a_balance + party_b_balance = total_deposit_stroops
   - Validated at: manager, store, contract (defense in depth)
   - Type: bigint (no floating-point precision loss)
   
3. SIGNATURE BINDING
   - Every commit signed by signer over message payload
   - Verified before recording to database
   - Contract also validates settlement signatures
   
4. REPLAY RESISTANCE
   - Vector clock prevents same sequence twice
   - Stale/backward sequences rejected immediately
   - Tested with concurrent rapid updates

5. DISPUTE WINDOW PENALTY
   - 24-hour challenge window: 86400000ms
   - Auto-submitted challenges: dispute-watcher.ts
   - Penalty amount: 100% of total_deposit_stroops
   - No appeals after challenge accepted

API ENDPOINTS
═══════════════════════════════════════════════════════════════════════════════

REST:
  POST   /api/v1/state-channels
         → Create channel: { channelId, partyA, partyB, totalDepositStroops }
         ← Channel metadata
         
  GET    /api/v1/state-channels/:channelId
         → Retrieve channel
         ← Channel state (OPEN|CLOSING|CLOSED|DISPUTED)
         
  GET    /api/v1/state-channels/:channelId/latest-commit
         → Get latest signed state
         ← Commit: { sequence, signer, balances, signature }
         
  POST   /api/v1/state-channels/:channelId/settle
         → Submit settlement: { finalSequence, partyAFinalBalance, partyBFinalBalance, merkleRoot }
         ← Settlement ID + status

WebSocket:
  GET    /api/v1/state-channels/:channelId/stream?token=...
         ↔ Bidirectional streaming of signed state updates
         → Heartbeat ping every 15s
         ← state_update: { messageType, sequence, balances, signer, signature }
